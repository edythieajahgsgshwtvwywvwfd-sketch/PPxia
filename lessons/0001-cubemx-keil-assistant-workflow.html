认清 CubeMX 根目录与 Keil 子工程

本节的目标：修改任何文件前，先判断它属于“硬件生成层”还是“业务代码层”。

它们不是两个项目

E:\32\clion_stm32\jishe_new3_6-12Mhz - new - 3\
├─ water.ioc          ← CubeMX 配置真源
├─ Core\              ← CubeMX 生成
├─ Drivers\           ← ST 官方驱动
└─ MDK-ARM\
   ├─ water.uvprojx   ← Keil 构建真源
   ├─ hardware\       ← 你的业务代码
   ├─ NVIC\           ← 你的通信/调度代码
   └─ system\         ← 你的全局状态和基础代码

当 VS Code 打开 MDK-ARM 时，标签中的 hardware/APP_MAIN.c 实际就是完整路径里的 MDK-ARM/hardware/APP_MAIN.c，并没有第二份文件。

最稳妥的编辑规则

可直接编辑

hardware、NVIC、system 下的自定义文件。

通过 CubeMX 修改

引脚、时钟、DMA、NVIC、TIM、UART 等生成配置。

如果必须在 CubeMX 生成文件里加代码，只能放进已有的 /* USER CODE BEGIN ... */ 与 /* USER CODE END ... */ 之间。ST 明确说明其他位置会在重新生成时被覆盖。

推荐工作方式

  1. VS Code 打开完整父目录。
  2. 在 Keil Assistant 中点击“打开项目”，选择 MDK-ARM/water.uvprojx。
  3. 关闭 CMake 自动配置，避免当前不完整的 CMake 清单干扰。
  4. 日常编译和下载仍走 Keil Assistant；修改硬件才打开 water.ioc。

一分钟自检

问题：需要把 UART4 波特率从 115200 改为 57600，应该先改哪个文件？

先改父目录的 water.ioc，再由 CubeMX 重新生成。不要只改 Core/Src/usart.c，否则下次生成会丢失。

问题：新增一个机械动作状态机，应该放在哪里？

放在 MDK-ARM/hardware 的自定义文件中，再把该源文件加入 water.uvprojx；不要把大量业务逻辑堆进生成的 main.c。

实践反馈回路

下一次改 CubeMX 前先提交/备份；生成后查看变化；在 Keil Assistant 中 Rebuild；确认 0 error；最后下载验证。任何一步异常都先停止，不要连续生成多次。
